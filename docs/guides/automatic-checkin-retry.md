# 自动签到失败重试策略与复盘

更新日期：2026-10-15

## 长期规则

- 自动签到按账号独立处理。一次失败后继续尝试，最多 **3 次总尝试**（首次 + 最多 2 次重试）。
- 重试等待分别为 5 秒、10 秒；成功或上游明确表示“今天已签到”时立即停止。
- 只有真实失败才重试。若只需恢复失败账号，应使用单账号入口，避免再次触发已成功账号。
- 签到服务运行在独立的 `workbuddy2api` 上游。上游进程须保持运行，主机也须在排程时间可用。

## 2026-10-15 运行复盘

- 一次自动轮次中，有账号收到上游 HTTP 500，业务码 `10001`，消息为“签到失败，请稍后重试”。这里的 `10001` 与“今天已签到”的正常幂等回复不同，应按真实失败处理。
- 随后只对失败账号逐个执行单账号重试；两个目标均在第一次重试请求中以 `code=0` 成功，管理端记录 2 条成功、0 条失败。
- 这次恢复证明定向重试有效，但没有触发自动调度器的失败重试分支。自动调度器的三次尝试逻辑已部署，仍需等待真实失败时从日志核实尝试次数和最终汇总；不应为验证而人为制造上游失败。

## 部署边界

本机部署的三次自动重试逻辑位于配套 `workbuddy2api` 的调度器中。该上游源码、运行配置、账号授权文件与二进制均排除在本仓库之外（根目录 `.gitignore` 中的 `/upstream/`）。因此本文记录策略与经验，但不代表每个 WorkBuddy Manager 发布包都自带此上游行为。重建或替换上游时，应确认新的上游实现仍遵守本策略，并在凭据安全的前提下验证。

## 安全记录要求

复盘仅记录时间、汇总、错误类别、尝试次数和结果。不要提交账号标识、手机号、访问令牌、Cookie、API Key、密码或上游配置文件。
